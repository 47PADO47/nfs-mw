# 0001 — Bevy as the game framework

- **Status:** proposed (2026-10-08). Needs the project owner's decision before any migration.
- **Milestone:** 4 (engine foundation).

## Question

Milestones 5–7 add physics, AI, races and menus. All of them are game objects, systems that update them each
tick, and events between them. Should those be built on Bevy, and if so, how much of Bevy?

Today the binary is a hand-written `winit` loop (`crates/nfsmw/src/viewer/app.rs`) that calls one `Scene`
trait object; rendering is our own `blackbox-render` on wgpu. That is fine for two viewers. It has no entity
model, no scheduling, no events, no gamepad input, no text or UI drawing.

## What we need from a framework

1. A way to organise many interacting game objects (cars, AI, traffic, triggers) and to order their updates.
2. Events between systems (collision, race finished, pursuit state).
3. Input with controllers, rebindable.
4. Text and UI drawing for the F12 console, the metrics overlay and, in milestone 6, the front-end menus.
5. Staying faithful: the game has its own streaming, its own fixed-step physics and its own look. The framework
   must not impose a renderer or a loop shape that fights those.

## Facts checked on 2026-10-08

| Fact | Consequence |
|---|---|
| Bevy 0.19.1 (stable) depends on wgpu **29**, glam 0.32. We use wgpu **30**, glam 0.34. | Bevy's renderer cannot share our wgpu types today. |
| Bevy **0.20.0-rc.2** (2026-09-28) depends on wgpu **30**, winit 0.30, glam 0.33, gilrs 0.11. | After 0.20 is final, wgpu and winit versions line up with ours. glam stays one minor behind. |
| Bevy is split into crates: `bevy_ecs`, `bevy_app`, `bevy_input`, `bevy_gilrs`, `bevy_winit`, `bevy_ui`, `bevy_render`… Each is MIT OR Apache-2.0. | Parts can be used without the renderer. |
| `bevy_ecs` needs Rust 1.95. The workspace says 1.88 (building on 1.98). | Adopting any Bevy crate raises our MSRV. |
| Bevy ships a breaking release about every 3–4 months. | Every adopted crate costs a migration per release. |
| `egui-wgpu` 0.36 targets wgpu 30 and winit 0.30. | An immediate-mode debug UI fits our renderer without Bevy. |

## Options

### A. Stay as we are; add `egui`, `gilrs`, our own settings, and `hecs` or hand-rolled objects

- Smallest change, no framework upgrades to chase.
- ECS, scheduling and events would be written by us in milestones 5–7, which is the part Bevy already does well.
- Gamepad support and rebinding are written by us.

### B. Bevy fully: move the viewers onto Bevy's renderer

- Gets UI, text, post-processing and shadows for free.
- Blocked until Bevy 0.20 is final (wgpu 29 vs 30), and then costs a rewrite of everything milestone 3 made
  work: reverse-Z infinite projection, pre-lit and sky shading, texture animation, zone-driven residency of
  ~600 tiles, instanced draws of ~80,000 scenery instances with our own culling and LOD rule.
- Milestone 8's car shader (`specs/car-assembly.md` §8) and the game's fog and lighting would be custom Bevy
  render-graph nodes anyway, which is the least stable part of Bevy's API.
- `blackbox-render`, built to be shared with other Black Box games, would be dropped or reduced to a plugin.

### C. Bevy as the shell, ours as the renderer ("ECS shell")  — recommended

Use Bevy for what is not rendering, and keep `blackbox-render`:

- `bevy_app` + `bevy_ecs`: the main schedule, a fixed-step schedule for physics, systems, resources, events.
- `bevy_input` + `bevy_gilrs` (+ `bevy_window` / `bevy_winit` if that integrates cleanly): keyboard, mouse and
  controller input as resources and events, replacing `viewer/input.rs`.
- `blackbox-render` draws into the window Bevy opens. It already creates its surface from a window handle, so
  it can be driven from a Bevy system (it stays in the `libs/` crate and gains no Bevy dependency).
- Debug UI (console, metrics): `egui` rendered by `blackbox-render` through an optional overlay hook.
  This is a stopgap for milestone 4; menus in milestone 6 are skinned FEng screens drawn by the game itself,
  not a general UI toolkit.
- `libs/` stays Bevy-free. Game crates (physics, AI, races) depend on `bevy_ecs`. Pure maths/rules (for
  example the vehicle model) can stay plain Rust functions that systems call, so they are testable without a
  `World`.

This keeps what works, gets the ECS where the game needs it, and leaves a later move to Bevy's renderer open
because nothing in `libs/` knows about it.

### D. ECS only: `bevy_ecs` + `bevy_app`, our own winit loop and input

Like C without `bevy_input`, `bevy_gilrs` and `bevy_winit`. Less churn per Bevy release, but we write
controller support and the window plumbing ourselves for no real gain, so C is preferred unless `bevy_winit`
turns out to conflict with our renderer's surface handling (see the check below).

## Decision (proposed)

Adopt **C**, on **Bevy 0.20** once it is released.

- Until 0.20.0 final, do not add Bevy dependencies: 0.19 would pull wgpu 29 into the tree through
  `bevy_render`'s dependants and it adds no value over waiting. The work that does not depend on the choice
  (layered settings, the `Settings` type, command-line and environment handling) goes first.
- Pin exact minor versions (`=0.20.x`) and migrate on our schedule, one Bevy release at a time.
- Raise `rust-version` to 1.95 in the same commit that adds the first Bevy crate.
- Keep glam 0.34 in `libs/`. Where Bevy's `Vec3` meets ours, convert at the boundary
  (`glam::Vec3::from_array`) instead of downgrading `libs/`.

## Check before migrating (a one-day spike)

1. `bevy_winit` + `blackbox-render`: can the renderer create its surface from the window Bevy owns without
   `bevy_render`? If not, fall back to D.
2. Frame pacing: our `--max-fps` limiter and `--no-vsync` must still work under Bevy's runner.
3. The `--screenshot` path renders offscreen with a hidden window; it must run without a full app loop.
4. `cargo xtask check`'s size and leak rules and `deny.toml` license policy pass with the Bevy crates.

## Consequences

- **Good:** gameplay milestones get an ECS, events, ordering and gamepad input without writing them.
  `libs/` stays reusable by any Black Box game.
- **Cost:** a higher MSRV, a longer first compile, and a migration per Bevy release for the crates we adopt.
- **Risk:** if the spike shows a window/surface conflict, the fallback (D) still gives the ECS.
- **Reversible:** only game crates depend on Bevy. Dropping it later means replacing `bevy_ecs` calls in
  those crates, not touching file-format or rendering code.

## Not decided here

- Whether to move to Bevy's renderer later (option B). Revisit in milestone 8 when the car shader and
  post-processing are specified.
- The settings menu (milestone 6).
